# 0006 个人信息、认证与订单详情

## 背景

在角色与订单申请流程稳定后，需要补齐“人”的信息与订单的深度查看能力：

- 新增“个人信息”模块：可修改资料、申请认证，并查看介绍、合作记录与认证；
- 区分昵称与实名：注册只需用户名/邮箱/密码，昵称由系统生成且可改；实名不进入个人资料，归属认证信息；
- 增加“实名认证”，与企业/工程师认证组成三类认证，并支持用户自行申请、管理员审核；
- 需求单（订单）需要独立详情页，展示订单信息、双方资料、工作日志和全部申请审批记录；
- 申请单展示当前审批人/时间/理由（订单详情列出该订单全部申请，形成历史审批记录）。

## 决策

### 昵称、实名与资料

- 注册字段收敛为 username / email / password；注册成功后自动生成 `用户{id}` 昵称，登录后可改；
- `users.full_name` 仅作为实名，个人资料页不可修改，只由“实名认证”审核通过时写入；
- 展示名统一为 `nickname → full_name → username`，订单/申请/日志/审批人都用昵称；
- 新增个人资料字段：介绍（bio）、技能标签（skills）、城市（city）、联系电话（contact_phone）、
  微信（contact_wechat）；邮箱可改（唯一校验），用户名不可改。

### 三类认证

```text
realname（实名）  ── 基础认证，可单独拥有
enterprise（企业）─┐
engineer（工程师）─┴─ 与实名叠加，二者互斥（新认证替换旧认证）
```

- 认证角色同样由 RBAC 角色承载：`realname` 是新增的无权限身份角色；企业/工程师仍保留；
- 用户提交认证申请，管理员在「认证审核」页通过/驳回；
- 企业/工程师申请前必须已有已通过的实名认证；
- 审核通过后授予对应角色并 `resync_user`；企业/工程师互斥，新通过时替换旧角色；
- 管理员用户管理不再直接改认证，只保留昵称/邮箱/启用/余额调整，认证统一走审核页；
- 订单等用户摘要改为 `certifications: ["realname", "enterprise"]` 列表，前端可展示多个认证徽章。

### 认证申请模型

`certification_applications` 保存三类认证的申请字段（实名：姓名/身份证号/手机号；企业：公司名/信用代码/
联系人/联系电话/资质说明；工程师：技能/工作年限/项目经历/联系电话）、状态（pending/approved/rejected）、
审批人/时间/理由。驳回后可重新提交；同类型 pending/approved 时不能重复申请。

### 个人资料与公开主页

- `GET /api/v1/profile` 返回本人完整资料（含邮箱/实名/联系方式）、认证、合作记录与统计；
- `PATCH /api/v1/profile` 修改昵称/邮箱/介绍/技能/城市/联系方式；
- `GET /api/v1/profiles/{id}` 是登录后可看的公开主页：昵称、介绍、技能、城市、认证徽章、
  合作记录（对方昵称/认证、完成时间、金额、角色、订单），隐藏实名、邮箱、电话、微信；
- 合作记录口径：已完成订单（我发布 + 我接单），按完成时间倒序取最近 20 条；统计完成单数、
  合作方数（去重对方）与累计合作金额。

### 订单详情与申请审批展示

- 新增 `/fde/orders/:id` 页面：订单完整信息、托管状态、发布方/接单工程师资料卡、工作日志、
  全部申请及其审批信息；按当前用户与状态提供操作（申请接单、取消、审批、提交日志、申请交付/确认交付）；
- `GET /api/v1/fde/orders/{id}` 的详情响应增加 `applications` 列表，包含每笔申请的申请人、审批人、
  审批时间与理由；订单详情页据此展示“历史审批记录”；
- 不做独立的申请事件流水表：当前审批信息已足够，列表保留全部申请行；如后续需要完整审计，
  可再扩展 event 表。

## 代价与后续

- 实名涉及身份证号等敏感信息，当前明文存储且仅本人/管理员可见，后续需要脱敏/加密与审计；
- 实名、企业、工程师认证共用一张申请表，字段较多且可空，靠服务层按类型校验；
- 认证无撤销流程（审核通过后只能由后续认证替换企业/工程师，实名不可撤销），后续如需撤销需补接口；
- 公开主页合作记录包含订单金额，属于产品选择；如隐私要求提高，可改为只展示统计；
- 管理员不能再直接改认证，认证必须走审核页，减少双入口但增加操作步骤；
- 昵称不唯一，可能出现重名；如需唯一需另加约束。
